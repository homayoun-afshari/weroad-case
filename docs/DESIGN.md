# Plan

This is the plan I made before writing any code: what I assumed, how I designed the assistant, and the choices I made along the way, with the reasons. It is a summary of my working notes. The write-up for WeRoad says what I built and what I left out; this file says what I set out to build and why.

**References to the brief.** The brief is the PDF "WeRoad take-home case - The assistant on the search page". It is not in this repository, so a reference is a location, not a link: "_Brief: §3 (p. 2), "Starts from the page"_" means section 3, on page 2, the bullet with that title. Sections 1 and 2 are on page 1, section 3 and the start of section 4 on page 2, and the rest of section 4 on page 3.

**Codes.** The design choices have letters (`DESIGN.md`, section 3): "choice A". The next steps and the suggestions for WeRoad have their own letters (`BUILD.md`, section 5): "next step B", "suggestion A".

**Other documents.** `UI_LAYOUT.svg`, `SEARCH_FUNCTION.svg` and `AGENT_GRAPH.svg` are figures, each with two diagrams: this plan on the left and the prototype as built on the right (the build is in `BUILD.md`). `SEARCH_FUNCTION.md` and `AGENT_GRAPH.md` describe the search function and the agent in full, with the input, output and an example of each part.

## 1. Premises

What I took as given before designing anything. Where the brief doesn't give it, the reference is to the data, and I say so.

### Assumptions

- **Today is 2026-10-16.** That is the date the data was exported (`exportedAt`). Every "past" and "upcoming" is measured from it, so the brief's example "I only have 19–24 October" behaves the same on any day the prototype runs. _Brief: §3 (p. 2), "Picks the right tool" (the example); "What we give you" (p. 3), the data and its dates._
- **I don't have WeRoad's Search API.** All I can count on is that it takes a search request and returns an ordered list of trips. Its classifier ("Smart filters") is announced, not shipped, so I can't rely on it. _Brief: §1 (p. 1), Search 3.0 and "A classifier will soon pre-fill filters"; §3 (p. 2), "Searches like the page does"._
- **The page and the chat stay in sync, and neither replaces the other.** WeRoad's A/B test of a chat-only page lost 36–41% of product clicks. There is one search state and the page always shows what the search function returns: the assistant changes the search request, and the page follows. So the two can't disagree, and "the list updates" comes for free. What happens on the page reaches the agent through the chat history. _Brief: §2 (p. 1), last paragraph ("help the page, not replace it"); §3 (p. 2), "Searches like the page does" and "Drives the page", and the paragraph on the guardrail._
- **The page never depends on the chat, and the chat costs nothing until the user writes.** Two callers use one search function, the search button and the agent, and only the agent's search gets an assistant message. Searching works without the model, so a model failure, its latency or its cost never blocks the page, and no model call is made unless the user writes. _Brief: §3 (p. 2), "Never a dead end" ("when something fails, it degrades gracefully") and the measure "latency"; §1 (p. 1), the chatbot "starts cold"._
- **Code, not the agent, loosens an empty search and ranks what it finds.** An agent trying combinations until something returns would be slow, costly, unbounded and inconsistent, and it might loosen what the user insisted on. Each search result carries the search state that found it, so the page can tag suggested results and the agent can explain them. _Brief: §3 (p. 2), "Never a dead end" ("zero results get the nearest options and the reason"); §2 (p. 1), "17% of text searches return nothing"; §4 (p. 2), "where the business rules live"._
- **Business rules live in code, with tests, never in the prompt.** They are listed under [Business rules](#business-rules). _Brief: §4 (p. 2), "where the business rules live"._
- **A simple agent on a stack I can defend.** One tool-calling loop, with the rules in the tools, so a reflection step would have little to check, and cost and latency stay low. The stack is Next.js with the Vercel AI SDK: no graph framework, no database, no deployment. I know it well enough to defend it line by line, and a list beside a chat is easy in it. WeRoad's stack (Vue/Nuxt, NestJS) would add risk without changing the design. _Brief: §4, "Time and format" (p. 3), "Any language, any model… a terminal or a bare web page is fine", and "I expect you to own the repo and its technical choices"; "We do not expect production code… You choose what matters in two and a half days"._
- **The agent speaks only when spoken to.** It reacts to user messages, never to page changes on its own: a page change by the user gets no assistant message, and the agent learns about it with the next user message. Proactive messages would push the chat over the page. _Brief: §2 (p. 1), the A/B lesson; §1 (p. 1), the chatbot "always starts cold"._
- **No approval before page changes.** The agent applies a change instead of asking "shall I set max €2,000?". Undo makes every change cheap to reverse, and the brief measures how often users undo what the assistant did, which assumes it acts. _Brief: §3 (p. 2), the success measures ("how often users undo what it did")._
- **Hand-over is a stub, offered only when the agent can't answer.** That is when the departures, itinerary or FAQ tools don't give the answer, or when the message is about the app but no tool covers it. A message unrelated to the app gets an honest "I can't help with that here". In the prototype, Yes freezes the chat; the real one swaps the model for a person in the same chat (next step B). _Brief: §1 (p. 1), "hands over to a human agent in Zendesk when it should"; §3 (p. 2), "Picks the right tool" (hand-over to a human)._
- **Nothing outlives the page session.** _Brief: §3 (p. 2), "Out of scope: … cross-session memory"._

### Business rules

Rules the code enforces, so the prompt never has to.

- **Only bookable departures count, and past ones are never offered.** A departure that starts before today is dropped, whatever its status. A trip matches a date, price, age band or private-room filter only through a departure it can be booked on, and the price shown for a trip is its cheapest bookable departure. _Brief: §3 (p. 2), "Picks the right tool" ("a trip's departures (dates, status, price, seats left)"); "What we give you" (p. 3), "10 upcoming departures… sales status, seats left"._
- **Bookability comes from the sales status, never from seats left.** In the data, 129 NOT_AVAILABLE departures still show seats left, and they are not bookable. The statuses fall into three groups. _Bookable:_ PLANNED, ALMOST_CONFIRMED, CONFIRMED, ALMOST_FULL; the first two are not yet confirmed and the user is told so, in the words of the FAQ's "Open to book" article (wait for confirmation before buying flights). That mapping is my assumption, since neither the data nor the FAQ links them by name. _Waiting list:_ WAITING_LIST; a seat isn't guaranteed, so the agent says so, offers a bookable alternative beside it and promises nothing about how the waiting list works. _Not bookable:_ SOLD_OUT and NOT_AVAILABLE, never offered. _Brief: §3 (p. 2), "No invented trips, prices or dates"; "What we give you" (p. 3), the sales status and the randomly perturbed seats._
- **A date window matches departures that lie fully inside it.** When none does, the nearest bookable departures before and after are offered, with how far they are from the window. _Brief: §2 (p. 1), "people with fixed dates get a 'no' instead of the nearest option"; §3 (p. 2), "Never a dead end" and the example "I only have 19–24 October"._
- **Filters come before the text.** A value set in a filter wins over the same value read from the search bar's text, and an empty search is loosened in a fixed order (dates, price, duration, the other filters, last the text) within a fixed number of calls. Suggested results are ordered by how little was loosened. _Brief: §1 (p. 1), the classifier "pre-fills filters from the free text"; §3 (p. 2), "Searches like the page does" ("the assistant decides what to keep, change or drop… the API's classifier extracts the filter values from the text")._
- **Facts come only from data, and FAQ answers only from retrieved articles.** Prices, dates and seats on screen are rendered from data. In the chat, the agent repeats only what its tools returned and never prints its own list of trips. When no retrieved article covers a question, it says it doesn't know and offers the hand-over. _Brief: §3 (p. 2), "Never a dead end, never a lie" and "Picks the right tool" ("'do I need a visa?' is a FAQ"); §1 (p. 1), the chatbot "answers from FAQs"._

## 2. Conceptual Design

How the prototype works, before any code. The terms are the ones the brief uses; where it has none, I name the part myself.

### UI

The figure is `UI_LAYOUT.svg`. It has the search controls on top, the results list at the bottom left, the chat at the bottom right, and a message box for errors and warnings.

- **The search controls** hold the search bar, the search filters below it, and the undo and search buttons. _Brief: §1 (p. 1), the "What" bar, "When" and the filters._
- **The results list** shows the search results. Each item shows the trip and, below it, its search tags. A result found for the search request has no tags; a suggested one says how it differs ("€1,120 · above your €800"). Each item links to the trip's page, which gives the guardrail something to count. _Brief: §3 (p. 2), the guardrail "product clicks" and "SERP engagement"; "Out of scope: … the trip page"._
- **The chat** holds only a start button when the app loads. Pressing it starts the chat, and the button disappears (choice A). The first assistant message is written by code from the page state ("You're looking at 3 trips for 'northern lights', from €1,219. I can change the search, check dates or answer questions."): no model call and no new search. The conversation lasts as long as the page session (choice B). _Brief: §3 (p. 2), "Starts from the page" ("no questions already answered, no new search just for opening") and the measure "the share of searches that open the assistant"._
- **Undo** is one button in the search controls. It restores the previous page state, whether the change came from the user or the assistant. The chat is not rewound: the undo is recorded as a page event, so the agent knows on the next turn (choice C). _Brief: §3 (p. 2), the measure "how often users undo what it did"._
- **The message box** shows errors and warnings from the search controls and closes itself after a few seconds. Agent errors show in the chat (choice P). _Brief: §3 (p. 2), "Never a dead end"._
- **A search with a chat draft:** the search runs as usual. If the input box holds a draft, the message box warns that it wasn't sent. The draft stays, and when it is sent, the agent learns about the search from the page events (choice O).

### State

- **Two histories, and nothing else:** the page history and the chat history. There is no history of the whole app. The page history is enough for undo, and the chat history only grows. _Brief: §3 (p. 2), "Out of scope: … cross-session memory"._
- **Both live on the client,** so the server is stateless and has no database (choice D). The page history grows with every new page state, tagged user or assistant, and undo steps back through it without calling the server.
- **The client sends the chat history with every chat request.** Each user message carries the page events since the last one, then the page state at that moment, as tagged blocks before the user's words (choice E). For example:

  ```text
  <page_events>
  user searched "northern lights" · max price €2,000 (2 results)
  </page_events>
  <page_state>
  search: "northern lights" · max price €2,000 · dates: none
  results (2): #9 Iceland (8 days, from €1,219), #11 Sweden (7 days, from €1,759)
  </page_state>
  I only have 1–8 December
  ```

  _Brief: §3 (p. 2), "Starts from the page" ("it opens knowing the query, the applied filters and the trips on screen")._

### Search

The figure is `SEARCH_FUNCTION.svg`, with this plan on the left and the prototype as built on the right. The search function is described in full in `SEARCH_FUNCTION.md`: why it is built this way, and the input, the output and an example of each of its parts. Here is what matters for the plan.

A search request goes through the translator, which gives the original search state. The mock API returns the raw search results for it. If they are empty, the suggester loosens the state and returns suggested search results, each with its own search state. The search function is the three together: in, a search request; out, the original search state and the search results.

- **One search function, two callers** (choices G and J). The search button (through a small API route) and the agent's `search_trips` tool (on the server, choice F) call the same function, so the page and the chat never disagree. When the search button calls it, the agent is not called; it sees the change as a page event with the user's next message. _Brief: §3 (p. 2), "Searches like the page does" ("every trip search goes through the same Search API, so chat and page never disagree") and "Drives the page"._
- **The translator** recognizes destination names from the catalog, trip types ("northern lights") and price phrases ("under 2000"); what it doesn't recognize stays as text. Destinations are a list, because people ask for more than one ("hiking in Brazil or Argentina end of September"); a place not in the catalog stays as text, and the agent says there is no trip there. It plays the role of WeRoad's coming classifier and is replaced by it (next step F). _Brief: §1 (p. 1), "Smart filters"; §2 (p. 1), the "Brazil or Argentina" example._
- **The mock API** keeps the data's order, so the only ranking is the suggester's. It matches whole words and applies the filters, and departure filters count only departures that can be booked. I made it a tight API, so it assumes only what I know the Search API does (choice H). _Brief: §1 (p. 1), "understand → retrieve → filter → rank, exposed as one Search API"; "Out of scope: retrieval and ranking changes" (p. 2); "a mock catalogue of a few dozen trips is fine" (p. 3)._
- **The suggester** runs only when the raw search results are empty (choice I). It loosens the original search state one value at a time in a fixed order, within a fixed number of calls, and each suggested result carries the state that found it. Since the text is dropped last, the results are empty only if no trip can be booked at all. _Brief: §3 (p. 2), "Never a dead end"._
- **When the results are suggested ones,** the page keeps the search bar as typed and shows them under a banner ("No exact matches. Closest options:"), each with its search tags. A manual search makes no model call. When the agent searched, it explains the suggestions in its message.

Why a search comes back empty, and who fixes it:

| Why it's empty                                | Who fixes it                                                  | Example                                   |
| --------------------------------------------- | ------------------------------------------------------------- | ----------------------------------------- |
| Too strict (price, dates, duration)           | **Code:** the suggester (choice I)                            | "under €800 in Japan" → closest €1,120    |
| Misunderstood (words don't match the catalog) | **The agent,** with one targeted new search                   | "New Year's Eve" → dates over 31 December |
| Not a filter                                  | **The agent:** adds a word to the search text (choice M)      | "cooking class" → "cooking"               |

_Brief: §2 (p. 1), "'USA', 'northern lights', 'New Year's Eve'… the trips exist; the intent is not mapped"; §3 (p. 2), "Reasons where search cannot" and "Never a dead end"._

### Agent

The figure is `AGENT_GRAPH.svg`, with this plan on the left and the prototype as built on the right. The agent is described in full in `AGENT_GRAPH.md`: the loop and its limits, and for each tool its input schema, its output schema and an example. Here is what matters for the plan.

- **One tool-calling loop** with the Vercel AI SDK: no reflection, no graph. A turn has a fixed maximum of steps, so its cost and time are bounded. The input is the system prompt (what the page blocks are, the rules on honesty and tools) and the chat history (choice E).
- **Five tools.** `search_trips` forms a new search request by keeping, changing or dropping parts of the current one and runs the search function in the same step, so it is the only one that changes the page (choice G); `get_departures` gives the departures that can be booked for the trips on screen and a date window (choice K); `get_itinerary` gives a trip's day-by-day plan; `get_faq` runs my small in-house retrieval over the FAQs (choice L); `hand_over` asks "Do you want to connect to a human agent?". _Brief: §3 (p. 2), "Picks the right tool" ("trip search, a trip's departures, the itinerary, FAQs, website pages, promotions, flight prices and hand-over to a human")._
- **The agent asks nothing the page already answers.** The page state in each user message carries the search, the filters and the results, so the agent works from them. _Brief: §3 (p. 2), "Starts from the page"._
- **Routing.** When the user changes **what** they want, the agent calls `search_trips`; when they ask **when** about the trips on screen, it calls `get_departures` and the page stays as it is. "I only have 19–24 October" is the second kind, "Something cheaper, max 1,500" the first. The rule is in the system prompt, and the eval set checks it (next step A). _Brief: §3 (p. 2), "Picks the right tool" ("'I only have 19–24 October' is a departures question on the trips on screen, not a new search; 'do I need a visa?' is a FAQ")._
- **When no trip on screen fits the window,** the agent doesn't search again on its own. It gives the nearest departures before and after and offers to look at all trips for those dates. A yes changes what is wanted, so it goes to `search_trips`. _Brief: §2 (p. 1), "a 'no' instead of the nearest option"._
- **Narrowing** ("only the ones with a cooking class") happens through `search_trips`: the agent keeps the search and adds a word to the text (choice M). This differs from the brief's wording, which says the assistant narrows "with its own reasoning"; I narrow by words, and narrowing by meaning is next step H. _Brief: §3 (p. 2), "Reasons where search cannot"._
- **Undo is not a tool.** If the user asks the chat to go back, the agent forms the earlier search request with `search_trips`: a new page state, not a step back in the page history, and not a press of the undo button, so it doesn't count toward the brief's undo metric (choice G).
- **Hand-over.** When the agent can't answer, it calls `hand_over` and the chat asks the question. Yes freezes the chat: a person is assumed to take over (next step B). The page keeps working. No closes the question and the conversation goes on.
- **During a turn** the search controls are locked and the stop button cancels the turn (choice N).

### Errors

- **An error shows where its action started** (choice P): search button errors in the message box, agent errors in the chat as an error message with a retry button. Both are written for the user.
- **A failed search keeps the last good results on the page.** A failed or timed-out model leaves the page fully usable. _Brief: §3 (p. 2), "Never a dead end" ("when something fails, it degrades gracefully and says so")._
- **A failed tool returns an error to the agent,** which tells the user instead of guessing.
- **When the agent doesn't know** (a visa), it says so and offers the hand-over.
- **The agent can't invent a price or a date on screen:** prices and dates are rendered from data, never from the model's text. _Brief: §3 (p. 2), "no invented trips, prices or dates"._
- **Agent errors are recorded in the chat history;** search errors are only shown in the message box, not stored (next step C).

## 3. Design Choices

The options I compared, what I chose and why.

**A. Chat start.** _Awake chat:_ it runs from the moment the app loads. _Loadable chat:_ it starts when the user presses a start button, which fills the chat until then. **Choice: loadable chat, with a first message written by code.** The brief's first metric is "the share of searches that open the assistant", which needs an opening to count, and pressing the button is that opening. Until then nothing runs, so a user who never asks for help costs nothing and sees a page that works on its own. A first message written by code knows the page without a model call or a new search, so starting is instant and free. _Brief: §3 (p. 2), "Starts from the page" and the success measures._

**B. Chat termination.** _Immortal chat:_ it lasts for the page session. _Mortal chat:_ it can be ended with a button. **Choice: immortal.** A mortal chat needs another button and a state with no conversation, and gives the user little, because closing the tab ends it anyway. Long conversations raise the cost per turn; a cap on the history sent to the model is next step E.

**C. Undo.** _Undo only_ or _undo and redo_; and for the scope, _page-only_ (the page goes back, the chat records it as a page event), _chat-only_, or _full_ (both go back). **Choice: undo only, and page-only.** The brief asks only for undo, as a metric, and redo is another button and more behavior to test (next step J). A full undo would erase conversation, but a user who undoes a change rejects the change, not the conversation. With a page-only undo, the agent sees "the user undid max price €2,000" and won't propose it again, and an answer that didn't touch the page isn't wiped by the next undo. The button sits with the search controls because it acts on the search. _Brief: §3 (p. 2), "how often users undo what it did"._

**D. Where the histories live.** _On the server_ or _on the client_, for both the page history and the chat history. **Choice: on the client.** The server stays stateless: no database, and any instance can answer. Undo needs no server call, so it is instant, and the chat history goes to the model on every turn anyway, so sending it costs only request size. The trade-off is that both are lost on reload, which is fine for one page session. In production I would keep them on the server (next step D).

**E. What the agent receives.** The whole page history plus the chat history; a fake user message for each page change; the page state in the system prompt, rebuilt on every request; or the chat history alone, each user message carrying the page events since the last one and then the page state at that moment, as tagged blocks. **Choice: the chat history alone, with the page blocks inside each user message.** The page history repeats the same results many times. A fake user message gets answered as if the user had spoken. A system prompt rebuilt every request can't be cached and loses the timeline. Anthropic's API has no system messages in the middle of a conversation, so the blocks go inside the user message, and the system prompt says they come from the page, not the user. The latest page state is then always right before the user's words, the input is smaller, and the start of the conversation can be cached. _Brief: §3 (p. 2), "Starts from the page"._

**F. Where the agent's search runs.** _Through the client:_ the tool sends the new request to the client, which calls the search function and sends the results back to the agent. _Inside the tool:_ the tool calls the search function on the server and returns one package; the client applies it and the agent replies from the same results. **Choice: inside the tool.** One round trip instead of two, and "same results, same order" by construction. Manual searches call the same function through a small API route. _Brief: §3 (p. 2), "Drives the page" ("the page refreshes with the same results in the same order")._

**G. The tool that changes the search.** _Two tools:_ one edits the search controls and one runs the search. _An edit-only tool._ _One tool:_ `search_trips` forms the new request and runs the search function in the same step. **Choice: one tool.** The results list must always be the result of what the controls show; a tool that only edits the controls leaves a price box at €2,000 while the list still shows a €2,539 trip. The agent also can't tell the user the outcome until the search has run, so it would write blind or guess, and two steps leave room to do the first and forget the second. Undo stays a button, not a tool. _Brief: §3 (p. 2), "Searches like the page does" and "Drives the page"._

**H. Mock API.** _Tight:_ a search state in, raw search results out. _Flexible:_ it also returns the state it understood. _Full:_ it returns results each with its own state, suggested ones included. **Choice: tight.** It assumes only what I know the Search API does: the classifier is announced, not shipped, and nothing says the API suggests anything. The translator and the suggester sit outside the mock, so if the API grows (suggestion A) or the classifier ships (next step F), they are removed, not rewritten. _Brief: §1 (p. 1), Search 3.0 and "Smart filters"._

**I. Empty results.** _Non-empty by design:_ suggested results are always added. _By replacement:_ they replace the raw ones only when those are empty. _By threshold:_ they are added when there are only a few results. **Choice: by replacement.** The brief asks for the nearest options on zero results. The suggester runs only when needed (one mock API call in the common case), and results with matches aren't padded with trips the user didn't ask for, so the page reads like a normal results page. The threshold is next step G. _Brief: §2 (p. 1), "17% of text searches return nothing"; §3 (p. 2), "Never a dead end"._

**J. Search function.** _Rule-based:_ the translator and the suggester in code around the mock API, with the agent calling the search function as a tool. _Agent-based:_ the agent turns requests into search states and calls the mock API, and the search button sends an empty user message that gets no reply. **Choice: rule-based.** With an agent-based search, every press of the search button is a model call, which costs time and money on every search, and the page stops working when the model does. It also matches the brief's split: the assistant decides what to keep, change or drop, and the classifier extracts the values. The code is deterministic and testable. The trade-off is that rules understand fewer phrasings than a model; the agent makes up for it in the chat by setting values directly. _Brief: §3 (p. 2), "Searches like the page does"._

**K. Departures.** _In the page state:_ each user message carries every trip's departures. _A `get_departures` tool._ **Choice: the tool.** Dates are the largest pre-booking theme in customer care (7.1k tickets in 3 months), and "I only have 19–24 October" is the brief's own example. The tool applies the rules in code: the sales status decides what can be booked, past departures are dropped, and the nearest bookable dates come back when the window has none. In the page state, the model would have to apply those rules itself, and 10 departures per trip would weigh on every message. _Brief: §2 (p. 1), the first bullet; §3 (p. 2), "Picks the right tool"._

**L. FAQ retrieval.** _In-context:_ the tool returns all the FAQs once, and they stay in the history. _Real RAG:_ retrieve the FAQs whose embeddings are closest to the message. _In-house retrieval:_ the tool returns the general FAQs plus those of the destination asked about, picked by the FAQs' own fields, and the agent answers only from what comes back. **Choice: in-house retrieval.** The FAQs I was given are 50 articles with a destination field, so picking by field is enough: one line of code, testable, and a small set the agent must answer from. Returning all of them would put about 10k tokens into every later turn. This says nothing about WeRoad's real help center, which is surely larger and in several languages; there a real RAG is needed (next step K). If nothing retrieved covers the question (a visa), the agent says so and offers the hand-over. _Brief: §1 (p. 1), the chatbot "answers from FAQs"; "What we give you" (p. 3), "50 public FAQs"._

**M. Narrowing ("only the ones with a cooking class").** _A `narrow_results` tool:_ the agent picks among the results by reading them, and the list shows that subset. _Narrowing through search:_ the agent keeps the search and adds a word to the text, which the mock API matches in the trip's text. _Cut:_ the agent says it can't filter by that. **Choice: narrowing through search.** In practice it applies when the chat calls the search function; without the chat, the user types "cooking" in the search bar to the same effect. It reuses the one path that changes the page, so undo, tags and sync need nothing new, whereas a narrowing tool needs the trips' descriptions in the agent's input and a second kind of page change. The limit is that it works only when the words are in the text ("cooking" finds trips 13, 15, 19, 24 and 40), not for meaning ("vegan food"; next step H). This is where I differ from the brief's wording. _Brief: §3 (p. 2), "Reasons where search cannot" ("narrows the trips it already holds with its own reasoning, and the page follows")._

**N. Changes during a turn.** _Lock:_ the controls are locked while the agent works. _Last write wins:_ whichever change arrives last stays. _Check:_ the agent's change applies only if the page hasn't changed since the turn began. **Choice: lock.** It is the simplest to explain and test; turns last seconds and the stop button is always there. Last write wins can silently throw away the user's own change. The check keeps the page usable during long turns and is the production answer (next step I). _Brief: §3 (p. 2), "Drives the page" and the guardrail._

**O. Search with a chat draft.** _Blocked:_ the search button is disabled while the input box holds a draft. _Warned:_ the search runs, and the message box warns that the draft wasn't sent. _Sending:_ the search button sends the draft to the chat. **Choice: warned.** The page never depends on the chat. A blocked search stops a user who typed half a question and then decided to search; a sending search turns a press of the search button into a model call. With a warned search the draft isn't lost, and when it is sent the agent reads the page as it is then, with the search among the page events. _Brief: §2 (p. 1), the A/B lesson._

**P. Error presentation.** _Single-source:_ every error in the message box, with a fixed message in the chat. _Verbose:_ agent errors in both. _By origin:_ each error shows where its action started. **Choice: by origin.** The user looks where they acted. Showing an agent error twice is noise, and a fixed message in the chat doesn't say what to do. Every error is written for the user, with a retry where it helps. _Brief: §3 (p. 2), "Never a dead end" ("it degrades gracefully and says so")._
